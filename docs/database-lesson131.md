# 第 131 题：连接池全局预算

学习目标：把单进程 sql.DB 限额累加为全局容量账，并能解释滚动发布 surge、全局预留与本地请求等待的取舍。

呈现采用实例池卡片、加和箭头、容量堆叠条与并列指标。操作采用参数操控、预测与理由记录、逐阶段推进、回退及诊断修复。阶段为原有 6 副本、目标副本、发布峰值、发布结束；参数变化开启新一轮。预测揭晓前记录且保持原文，反馈用可追踪算式解释差值。

帮助四种：示例比较 30/15/12；关系图联动单池与全局加和；分步推导列出核算约束；换输入挑战允许修改预留与 surge，寻找整数容量边界。全部为辅助探索，不写正式成绩。

模型只计算池配置上限。每实例一个池、请求均匀且每请求借一条连接；本地等待是未释放连接的单时刻快照，不包括数据库拒绝后的等待，不模拟真实耗时、吞吐或 P99。多个 sql.DB 须另外累加；0 在真实 Go API 中意味着不限制，因此本实验只允许正数池上限。容量预算可能无法支持任何正数上限，该情况明确提示修改约束。

测试覆盖副本扩容、surge 溢出、整数边界、预留耗尽、局部等待权衡、预测不可变性、回退及输入拒绝。所有控件可键盘操作；窄屏布局换行，关系图仍保留箭头与文字，颜色不是唯一证据。
