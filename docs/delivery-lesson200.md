# 第200题：架构投资验证实验

## 文件和入口

- `src/components/delivery-lab/lesson200/index.tsx`：默认无参主实验，命名导出 `Help({mode})`，支持 example / diagram / steps / try。
- `model.ts`：纯函数 `evaluate`、`initial`、`advance`。
- `style.css`：仅 `.d200` 范围样式，窄屏网格自然换行；range margin 为 0。
- `tests/delivery-lesson200.test.ts`：9 项模型测试。

## 教学目标与边界

依据用户指定教学设计文档，用参数操控、对照比较、预测验证与分步过程，检验“方案是否作用于瓶颈”和“经济指标是否能抵消硬约束”。所有数值是人为教学假设，不代表真实 ROI。成本按人日明确分为迁移、双维护和三个月新增运维，交付周期、延迟、事故影响与隔离分别呈现，不合并成总分。

硬隔离定义为独立身份、数据访问与部署边界。本模型只有拆分切片投入达到16人日才代表完成这些边界的试验验证；不是声称真实世界投入16人日即可证明合规。只拆进程没有自动满足隔离。未满足硬隔离时，即便延迟改善，也不能扩大。已满足硬隔离可成为继续验证的独立理由，无需伪造短期性能收益；预算和延迟护栏仍生效。

共享数据库热点时直接拆服务保留热点并增加网络开销；修热点和回滚分别改善延迟和事故影响。组织需要发生变化时，多团队独立部署可能合理。较少团队的协调问题也可通过模块化单体交付治理改善。模型不预设永远拆或永远不拆。

## 操作契约

主根 `data-testid=delivery-lab-200`。活动模型为 `data-testid=live-model`，`data-state` 为 JSON，含 config / plan / phase / prediction / reason / locked / outcome / traffic。配置先选瓶颈、团队数、试验投入、预算和硬隔离，再选择执行路线。预测和非空理由提交前单步不可用。

- `data-delivery-action=step`：从基线进入成本，再到10%试验、阈值审议、后续动作，共4次推进。
- `data-delivery-action=back`：回到前一模型快照，不解锁本轮预测。
- `data-delivery-action=reset`：保留当前配置，清空本轮预测和历史，开始新试验。

执行第一步后配置和预测冻结；原始理由原样保留，含首尾空白。步骤 1 不揭晓测量；步骤 2 才显示对照结果；步骤 3 显示因果判定与预测差异。回退表示回看教学历史；实际业务回切在步骤4显式显示。回切后未满足的隔离要求仍然未解决，页面不会将原基线标为合规解。

默认：数据库热点、2团队、12人日、无硬隔离，直接拆分没有目标改善，最终停止回退；修热点方案可扩大下一小切片。换为协作瓶颈、5团队、16人日，拆分能通过目标和护栏，扩大至20%继续验证。

## 四种帮助

- example：另一个仓库团队发布窗口实验，改团队数与独立发布边界，分别看等待和新增值守。
- diagram：点击调用方或共享数据库，联动影响节点，切换共享查询索引观察两条依赖路径变化。
- steps：按顺序展开问题证据、可否定假设、事前停止条件、反证与回切行动。
- try：新的强制隔离情境，先判断及原始理由，提交后锁定并揭晓，明确不记独立掌握。
