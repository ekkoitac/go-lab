# 第 146 题：重复投递与一次积分效果

依据用户指定的《学习-知识点教学中的交互与呈现方式》设计：呈现是投递卡片、两个消费者的内存、持久数据库及事务暂存；交互是预测理由、单步执行、崩溃干预、回退、改变事件键与诊断修复。各视图由一个纯状态模型派生，不是切换静态说明。

## 学习目标与模型

识别稳定业务事件 ID 与每次投递编号的差别；解释内存去重跨重启/多实例的失败；区分两种独立提交顺序的漏处理/重复窗口；观察持久 inbox 与副作用同事务的提交/回滚；构造超出去重保留期的反例。

八阶段：准备、首次投递、第一项写入、提交或崩溃、改变重投条件、再次投递、检查/第一项写入、完成重投。固定同一 payment-e1，每次副作用 +10；只有首次处理可注入崩溃，重投最终成功。提交成功后默认模拟确认丢失。内存只属于单个实例；inbox 和积分在模型中持久化。事务有可见暂存状态，提交前崩溃不保留任一写入。

默认是先加分后标记且中途崩溃，最后 20 分。先标记后加分崩溃为 0 分；同事务为 10 分。内存 seen 正常重投为 10，重启或换 B 为 20。错误的投递编号即使搭配同事务也会重复加分。7 天记录在第 8 天清理，积分不清理，历史重放再次加分。

这只是顺序内存教学模拟；不是真实数据库、不证明并发安全，生产需持久数据库事务和并发唯一约束，同库假设不覆盖外部服务副作用。超过保留期需要扩展去重语义或重建独立投影。无吞吐与延迟测量。参考 RabbitMQ reliability https://www.rabbitmq.com/docs/reliability 与 confirms https://www.rabbitmq.com/docs/confirms。

## 四种帮助

- example：同事务下切换支付事件/投递编号的登记键，同步看到 inbox 条数与积分。
- diagram：勾选把 inbox 和积分放进同一事务，移动提交边界；图示第一次崩溃的持久结果及重投后积分。
- steps：逐步执行同事务处理后重启的完整协议；可回退重置，显示暂存、提交和跳过。
- try：选择当天或第 8 天重放，输入预测与理由后验证保留期反例；输入变化清空已揭晓反馈。

所有状态仅存在组件内，不写正式成绩/掌握度。按钮支持原生键盘；焦点可见；使用可换行网格，无固定宽度，适配窄帮助栏与 390px；无依赖动画，reduced-motion 显式覆盖。
