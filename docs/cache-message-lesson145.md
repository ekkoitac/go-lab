# 第145题：Redis 故障与有界回源

## 教学目标与设计依据

依据用户指定《学习-知识点教学中的交互与呈现方式》：分流图和容量条是呈现；调参、预测理由、单步回退、目标反推和反例检验才是交互。学习者要解释 99% 命中隐藏了 100 倍灾难回源，能把准入放在数据库调用前，并按业务选择陈旧或拒绝。

## 动手观察

基线 100000 QPS × (1 − 99%) = 1000 QPS。预测故障后的容量结果并填写理由后，断开 Redis。图中每个流量分支由同一模型计算，保持 cache + online + stale + rejected = traffic。无界时全部回源超过 3000 容量；被放入数据库的请求不能伪装成入口快速拒绝。

回退到起点后可以启用共享预算、设置 1500 / 2500 / 3000 / 5000 QPS，切换商品展示与权限业务。Redis 重新连接时冷缓存仍为 0% 命中，在线请求优先使用准入预算，预热只能使用余额；每次推进恢复 10 秒。数据库超载时冻结成功填充，用于表达故障扩散，不估计超载时实际完成吞吐。

默认高流量无界回源用于暴露错误。回退保留参数、预测和理由；修改参数清除预测且回到基线；重置恢复默认配置。总请求率 100 QPS 是“直接回源必然故障”的边界反例。

## 四种帮助

- example：相同容量下，切换 100000 与 100 QPS 对照，直接修改分流和容量图。
- diagram：装拆准入门、切换权限业务，两种干预直接改变回源/陈旧/拒绝路径。
- steps：有界与无界激进预热方案，逐步走过正常、故障、冷恢复与填充。
- try：权限业务目标反推，要求保留 500 QPS 余量，先预测拒绝数和解释旧权限问题再验证。1500、2500 都可行，反馈说明吞吐与拒绝的取舍。

所有状态只在组件内，不触碰正式答题成绩或持久学习记录。

## 明确的模型边界

预算为每秒请求数，不是并发槽位。耗时未建模，不能把 3000 个并发槽视作 3000 QPS。恢复假设 10 万个等热键，每个成功源读取填入一个不同冷键，最多填入 99000 键对应 99% 命中；这是可复现的理想化恢复库存，不是生产流量模型或恢复时间承诺。真实系统有重复键、耗时、热点、错误与有限陈旧可用性。陈旧副本被假设独立于故障 Redis，且只有业务允许、有副本的请求能使用。

## 验证与 E2E 操作路径

目标单测：`node --import tsx --test tests/cache-message-lesson145.test.ts`。

主实验根 `cache-message-lab-145`，帮助根 `cache-message-help-145`，状态 `live-model` 的 `data-state` 包含 step、config、phase、dbTotal、stale、rejected、filled、prediction、reason。三个主动作均有 `data-cm-action=step/back/reset`。

1. 主实验：选择“先预测：故障后数据库会怎样？”为“回源超过 3000 QPS”；“写下依据：流量去了哪条路径？”填写理由；点“记录预测并断开 Redis”；读 online=100000、overloaded=true。
2. 点“回退一步”；“回源策略”选“在线与预热共用准入预算”；重新填写预测“不超过”与理由；点开始。验证 online=2500、stale=78000、rejected=19500、overloaded=false。
3. 点“恢复 Redis 连接”，验证 hitPercent=0；点“推进恢复 10 秒”，filled 增加，dbTotal ≤2500。回退应恢复原 snapshot。
4. 回退起点，把“业务读取”设为“余额 / 权限：必须读权威值”；再预测开始，stale=0，rejected=97500。
5. 帮助 try 中选择“权限业务的回源预算”为2500，“预测入口快速拒绝 QPS”填97500，填写“解释为什么不返回旧权限”，点“检验容量与业务约束”，出现“目标达成”。
6. 帮助 diagram 点“改为权限校验”使陈旧归零；点“拆掉准入门”使数据库入流100000。
7. 帮助 steps 点“执行恢复下一步”两次，进入冷恢复；“推进填充 10 秒”改变库存和命中率。
