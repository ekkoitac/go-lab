# 第 150 题：快照比版本，增量补缺口

依据《学习-知识点教学中的交互与呈现方式》：先定义可检验的学习目标，再选择状态面板与时序图；每个控件改变契约、规则、事件投递或学习者的预测，不用展开文本冒充交互。

## 学习目标与典型误解

- 理解完整状态快照携带当前结果，而增量只携带一笔效果。拒绝旧快照的规则不能照搬到增量流。
- 理解业务版本、事件时间与到达顺序分别表达什么。时钟偏差与网络重试可让后二者不反映业务因果。
- 看到水位 v3 并不能证明所有增量都已执行；必须核对连续水位、应用记录与缓冲。

## 动手观察

同一订单初始 v1 / 已创建 / 0 元。从付款人视角，v2 付款 -100 元，v3 退款 +100 元。先投递 v3，再投递/缺失 v2，随后重复/超时、核对、回补。用户选择完整快照或增量、接收规则及 v2 的链路，先给出最终净额预测和理由，才允许推进。每步展示消息、门控动作、版本、金额、缓冲与已应用记录，并明确不变的原因。回退重算确定性状态；重置保留配置并清除预测。

错误分支可见：到达顺序覆盖让快照退回 v2 / -100；更高版本门控用于增量，让 v3 的 +100 执行但 v2 的 -100 被丢掉。正确增量分支在 v1 缓冲 v3，v2 迟到或回补后顺序执行 v2 → v3。

## 四种帮助

- example：把信封在完整对账单与单笔流水之间切换，同一投递阶段联动门控与状态；可前进、回退。
- diagram：用到达序号、事件时间或业务版本排序并实际驱动快照覆盖，暴露“时间较晚即状态较新”的误解。
- steps：扮演版本门卫，必须选择缓冲、应用或忽略，依据连续水位逐步处理三个消息；错误选择有可操作的纠错依据。
- try：针对缺失 v2 的增量事故，从起点选择规则重跑并先预测回补结果，区分缓冲恢复与错误水位吞掉回补。规则切换不冒充修复既有投影。

## 模型边界与验证

单订单、统一单调版本、每个版本内容唯一。快照只更新投影，不代替真实扣款副作用；增量效果与连续水位生产中需原子持久提交。固定时钟偏差仅演示不能用墙上时钟推断因果。没有模拟多写者冲突、持久化故障和实际 broker。辅助操作不写正式成绩。

纯模型测试覆盖快照回退与门控、等版重复、增量错误跳版、缓冲去重、按序追平、超时不假造效果、可靠源回补、三类顺序差别、预测门控及回退。集成根节点为 cache-message-lab-150 / cache-message-help-150，live-model 的 data-state 为 {physical, config, prediction}。
