# 第39题：panic/recover 的恢复边界

依据用户《学习-知识点教学中的交互与呈现方式.md》，核心为可追踪的调用关系、栈展开与返回位置，而不是播放预写结论。

| 设计项 | 本题设计 |
|---|---|
| 学习目标 | 判断是否满足同goroutine、被延迟函数直接调用recover两个条件；解释恢复后边界返回，业务副作用仍然存在。 |
| 典型误解 | 任何defer内部间接调用recover都行；所有helper都无效；父goroutine能恢复子goroutine；恢复后从panic下一行继续；恢复会自动回滚。 |
| 核心关系 | 当前goroutine调用栈、直接调用关系、defer展开与边界返回。 |
| 呈现形式 | 栈顶明确的可执行调用栈、独立goroutine区、代码位置、panic/recover值、业务半成品和调用者结果。 |
| 交互任务 | 选择五种恢复策略，单步压栈/修改业务/触发panic/展开/执行defer/返回；回退、重置；把catch本身直接defer进行修复；对照直接与包装调用。 |
| 模型反馈 | 操作驱动纯状态机，每一步显示变化与原因。直接延迟catch可恢复；延迟闭包普通调用catch得到nil；未恢复panic模拟程序终止。 |
| 帮助方式 | example：可接线的车间故障保护类比；diagram：代码、被延迟函数与recover直接调用者关联探索；steps：固定有效边界的完整可逆展开；try：后台缩略图任务的新情境，提交结果、后续语句预测及理由再揭晓。 |
| 独立验证 | 本模块与帮助不计正式成绩；迁移题更换配置清除旧预测/揭晓，独立掌握仍由既有测验承担。 |

## 精确语义

- `defer catch()`且catch函数体直接recover有效。`defer func(){catch()}()`的catch是普通调用，其recover无效。代码以局部catch函数值演示两者只差一层调用。
- 当前goroutine中的panic沿当前栈展开，另一goroutine的defer不因它执行。未恢复的panic终止整个程序，不只是结束子goroutine。演示只模拟结果，不实际抛出浏览器异常。
- 有效恢复之后，包含恢复defer的边界函数完成返回，插件的panic后成功语句不执行。
- recordFailure是模型显式记录失败的操作；recover不自动形成error，也不修复半完成业务状态。
- 本模型使用非nil字符串panic，省略其他defer、panic(nil)、多次panic等情形。正常预期失败通常用error。

## 验证

纯模型测试覆盖直接闭包恢复、直接defer命名函数、包装间接调用、跨goroutine、无恢复、真实栈帧变化、恢复前后返回阶段、业务状态不回滚、故障后语句不执行、不可变回退重放与终态幂等。
