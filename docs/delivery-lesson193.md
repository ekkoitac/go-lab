# 第 193 题教学交互设计

目标：区分经过时间、接收确认、结果写入、完成信号，解释明确同步关系为何比 sleep 更可靠。

## 动手观察

- 同一可控 worker 调度过程并排对照 sleep 断言与等待 done；不是两个不同负载下的比较。
- 控制 worker 接收时隙、sleep 时隙、总预算；注入漏关 done 故障。
- 单步释放 gate、推进时隙，回退恢复完整状态；事件日志解释每次变化。
- sleep 太短显示提前断言；sleep 较长也只显示值碰巧已写入，不声称同步安全。
- done 缺失时即使结果已写入仍会超时；补上 close(done) 后可重跑验证，但预算过短仍失败。

## 换个方式理解

1. example：账单服务的接收确认与完成确认。选择等待信号并驱动服务阶段，对照“被接收”与“可安全读取”。
2. diagram：可选节点、可断开关系的同步证明链；断掉任一程序顺序或 channel 同步边，证明不成立。
3. steps：逐步为测试与 worker 排列协议操作，检验具体首个缺失前提，支持撤回修复。
4. try：未揭晓的取消任务情境，先判断并说明理由，再显示退出确认与清理顺序反馈。仅核对选择；文字理由供自查，不宣称语义评分，不写服务器掌握记录。

## 模拟边界

时隙不是毫秒；接收后固定下一时隙写入，再下一时隙关闭 done。同一时隙先处理 worker 事件，再检查测试与总预算。真实 select 多分支同时就绪不保证这种优先级。模型采用观察者视图，未执行不安全 Go 读取；仍需要 race 检查及其他交错、失败和取消路径测试。
