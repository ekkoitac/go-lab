# 第 134 题：跨行不变量与写偏斜

## 目标与误解

学习者通过亲自选择甲乙事务的执行顺序，构造两个事务都看到两人在线的执行，解释“分别锁住不同的医生行”为什么仍会破坏至少一位在线。进一步区分锁等待与快照更新，并理解 SERIALIZABLE 中止后的重试必须重新读取和重新判断。

## 交互与呈现

依据《学习-知识点教学中的交互与呈现方式》采用角色调度、预测验证、反事实干预与诊断修复。呈现为两个事务泳道、已提交视图、每个事务的固定快照或下一语句视图、读数和暂存写入。每次动作要求记录结果、在线人数与理由；揭晓后显示原预测、实际效果与状态变化依据。回退还原完整状态并移除后续预测，策略切换开启新一轮。

## 模型与边界

纯函数 advance 驱动 lock → read → decide → commit。共同锁在读取人数之前取得，人数统计独立为下一次动作，明确是新的 SQL 语句。READ COMMITTED 的每次查询读当前已提交值；REPEATABLE READ 在首次申请锁时建立事务快照，即使该锁操作等待也不刷新。本题共同排班记录仅锁定、不修改，因此不会借共同记录的写冲突保护跨行谓词。

SERIALIZABLE 用受限的两事务冲突模型在提交处中止第二个冲突提交者，丢弃暂存写入，完整重试会清除快照、读数和决定。此模型不是 PostgreSQL 的完整 SSI 算法，不承诺真实中止时机或牺牲者。未连接真实数据库、未做数据库实测；真实系统必须验证目标版本、隔离级别以及所有写者是否遵守共同锁协议。

## 换个方式理解

- example：共同锁场景的可回退示范，保持同一调度顺序切换 READ COMMITTED / REPEATABLE READ。
- diagram：在同一时刻追踪指定事务的快照来源、读数、判断关系，并替换隔离级别比较。
- steps：两个可选修复协议的 SQL 伪代码分步核对，包含共同锁与新语句边界、40001 完整重试。
- try：改成两个供货点停机的迁移练习，先提交结论与理由才显示执行结果。揭晓后的尝试明确属于辅助探索，不写正式成绩。

## 验证

模型测试覆盖只锁自己的行的并发反例及串行对照、共同锁 READ COMMITTED 的新快照、REPEATABLE READ 等待不刷新快照、未提交写入不可见、两种提交顺序下 SERIALIZABLE 中止与完整重试、预测记录不可变、完整回退。样式均在 db134 范围内，600px 以下泳道改为单列；所有控制使用原生键盘可访问的按钮、选择器和输入控件。
